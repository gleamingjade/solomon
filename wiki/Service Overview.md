# Service Overview

## What Does Solomon Do?
갈등 상황에서 서로의 입장을 밝히고 이를 기반으로 이야기를 나누면 ai가 종합적으로 판단 후
누가 잘못했는지 판단하는 서비스.

## Trial Flow
1. 재판(trial) 생성 후 상대방에게 링크 전달

생성 시 개략적으로 사건을 나타내는 제목, 재판에서 사용할 닉네임을 입력해야 함.

2. 상대방 접속

재판에서 사용할 닉네임을 입력해야 함.

3. 재판 시작 준비 완료 요청 시스템 메시지 도착

각 유저는 시스템 메시지 버블 속 준비 완료 버튼을 통해 본격적인 재판을 시작할 수 있음.

4. 각자의 입장 서술 요청 시스템 메시지 도착

둘 다 준비 완료 요청 수락 시 해당 사건에 대한 각자의 입장을 서술할 수 있는 다이얼로그를 제공함.

시스템 메시지 버블에 입장 서술 버블을 눌러 다이얼로그를 열 수 있음. 해당 서술은 db에 저장되며 추후 ai의 최종 판결에 사용됨.

5. 논쟁

둘 다 다이얼로그 제출 완료 시 양 측에 서로의 서술이 공개되고 이를 기반으로 논쟁한다.

6. 최종 판결

더 이상 말이 통하지 않을 시 최종 판결을 요청할 수 있다. 서로의 서술, 채팅 내역이 
ai에게 보내지고 llm이 누가, 왜 잘못인지 판단을 내린다.



# 기술적 고민.. ..
solomon 서비스에서 채팅을 비동기으로 구현할 시 치명적인 엣지 케이스

메시지가 채팅 서버에 도착하면 웹소켓을 먼저 쏘고 채팅 메시지를 비동기로 저장한다고 했을 때,

처리량이 많아져 db에 병목이 생겼고, 상대방은 오프라인이라 웹소켓으로 메시지를 못 받았다.



이후 상대방은 재접속 및 채팅방 최근 메시지 내역을 불러왔고, 그동안의 메시지는 아직 db에 없다.

비동기라 실시간성은 유지돼서 과거 히스토리를 최신 내역이라고 믿은 맥락이 깨진 채로 유저가 실시간 채팅을 이어간다.



위 상황은 비동기식 채팅을 내 서비스에 적용했을 때 충분히 발생할 수 있는 아주 치명적인 시나리오다.

solomon 서비스에서 발생하는 모든 채팅은 자잘못을 가리는 싸움 상황이다.

이러한 전제 조건에서 위 엣지 케이스는 사실상 서비스의 실패나 다름없다.



해결법: 채팅방 메시지 처리 -> 웹소켓 fanout 동기식 전환

low latency를 포기하고 웹소켓 fanout 전 채팅 메시지 관련 작업을 처리하면 해당 문제를 원천 차단할 수 있다.



채팅 메시지 관련 작업이란 채팅 메시지가 발생하면 따라오는 여러 파생 작업을 의미한다.



예를 들어,

채팅 메시지가 발생하면 해당 채팅방에 참여중인 유저들의 채팅 목록에 해당 채팅방이 상위로 정렬돼야 한다.

채팅 목록에서 보여줄 미리보기 카드에 마지막 메시지 정보(내용, 시간), 안 읽은 개수 등도 업데이트돼야 한다.



채팅방 메시지의 경우 사용하는 인덱스 해봤자 시간순 정렬이라 항상 증가하니 인덱스 트리의 마지막에 '삽입'만 하면 돼서 빠르지만

유저별 참여중인 채팅방 정렬은 인덱스 삭제, 위치 탐색, 삽입을 동반하기 때문에 '상대적'으로 오래 걸린다.



따라서 채팅방 메시지만 동기식으로 처리하고 파생 작업은 비동기로 하면,

채팅 중 메시지 조회 불일치를 해결하면서 최대한의 속도를 낼 수 있다.



한계 돌파: lsm-tree로의 전환

b-tree는 읽기에 최적화된 자료구조다. 반면 lsm-tree는 쓰기에 최적화된 자료구조다.



rdb를 사용하는 것보다 lsm-tree를 사용해서 위의 채팅 메시지만 동기식 구조를 구현하면 더욱 성능을 향상 시킬 수 있다.



scylla db를 사용했다.

유저가 정말 많아져 동기식이라는 구조적인 문제 때문에 문제가 될 만큼 처리가 지연 될 수도 있다.

앞에서 언급한 치명적인 엣지 케이스 때문에 구조를 바꿀 수 없으니 db 처리 속도를 향상 시켜야 한다.

scylla db는 lsm-tree로 매우 빠르며 에초에 수평 확장을 전제로 설계된 db라 노드만 추가하면 샤딩이 가능하다.



진행중인 재판의 채팅방 메시지(핫 데이터)는 쓰기에 최적화 된 scylla에 동기로 쓰고, 읽는다.

종료돼서 더 이상 채팅이 발생하지 않는 채팅방 메시지(콜드 데이터)는 rdb로 옮겨 놓고 읽기에 최적화된 rdb에서 읽는다.
